# codemode 沙箱选 rquickjs，执行模型是「一次执行一个专职线程加一个 VM」

触发器的两条核心能力——模型写的采集脚本、复合条件脚本——都需要一个可嵌入的脚本引擎，语义对齐 pi 的 codemode：脚本是 async 函数体，能 `await` 宿主调用，有 `store`，输出受限，沙箱里没有文件系统与网络「随便用」的入口。三个候选里，**rhai 证伪**：它没有 `await`，而「脚本调 async 宿主函数」正是这套设计的中心。**boa 备选**：纯 Rust、无 C 工具链，但 `Context` 是 `!Send`、async 只能靠 `future::block_on` 阻塞驱动、没有等价的中断入口，超时只能靠杀线程。**选 rquickjs 0.14**（features `futures` + `macro`），代价是多一条 C 工具链依赖。

执行模型照搬 pi：**每次执行一个专职线程**，线程内建 current_thread tokio runtime + `LocalSet`，创建独立的 `AsyncRuntime` / `AsyncContext`，跑完销毁。不开 `parallel` feature：QuickJS VM 不跨线程共享，共享只会把「一个脚本卡住」传播成「一片脚本卡住」。并发上限 2~4（每次执行一个线程），超限排队——采集与判定本来就是低频任务，把上限压低换来的是内存与故障面的可预测。

有两个坑必须写进实现约定，否则脚本会**静默挂死**：其一，`ctx.spawn` 出去的宿主 future 必须有 `drive()` 被 poll，否则脚本会 await 一个永不 settle 的 promise；其二，超时必须双保险——`set_interrupt_handler` 掐 JS 自旋，外层 deadline 兜住「宿主调用还在途」（网络请求卡住时 JS 根本没有自旋可掐）。另外**不能开 `rust-alloc`**：开了之后 `set_memory_limit` 变成 noop，内存上限形同虚设。

沙箱能力按白名单注册，别无其他：`collect` 拿到 `http` / `fs`（默认只在 workspace 内，越界须 `allow_paths`）/ `secret` / `log`；`judge` 拿到冻结快照 / `store` / `log`；两者共用 `now` / `boot_at` / `uptime_s`。**不给 `shell` 与 `exec`**：这段代码是模型写在磁盘、由 tick 无人值守执行的，风险等级与交互式工具调用不同——人会看一眼命令，tick 不会。**不给 `sleep`**：它只会吃掉超时预算却看起来在工作。**`judge` 不给任何网络与文件能力**：判定本该是毫秒级纯函数，允许它现取数据等于亲手毁掉「同一 tick 内所有脚本看到同一瞬间」。

`store` 不单独落文件，塞在 `state.json` 里（≤16KB）。一份状态一个文件、一个写者、一次原子替换；分成两个文件就要两次原子写，还会出现「状态写了 store 没写」的中间态。

**实测（2026-10-31，探针留在 `.scratch/codemode-probe/`）**：在本环境直连 crates.io 拉 `rquickjs-sys` 连续四次 30s 超时，换稀疏镜像（rsproxy）才下到——这是网络问题而非 crate 不可用，CI 里同样要为它准备镜像或在构建机上预置缓存。拿到源码之后，tokio `full` 加 `rquickjs`（`futures` + `macro`）的全新 release 构建是 **14.3 秒**，其中 `rquickjs-sys` 用系统 `cc` 编 QuickJS 的 C 源码，不需要额外系统依赖；同 profile（release + strip）下 tokio-only 基线 623,664 字节、加上 rquickjs 1,414,352 字节，**净增 772 KB**。证伪条件里的两条（+10MB、CI 超 5 分钟）都没有触发，也不接近，所以引擎选择按原样保留。顺带测到一条对未来实现有用的：每轮新建再销毁一个 VM 只要约 0.1 毫秒（200 轮 21 毫秒），因此不需要池化，一次执行一个 VM 的开销可以忽略。

行为侧的四条实测同样写进实现约定。裸 VM 的全局面里 `require` / `process` / `import` / `setTimeout` / `setInterval` / `fetch` / `console` 全是 `undefined`，但 JS 内建的 `eval` 与 `Function` 构造器是函数——它们在 VM 内部仍有数，不构成逃逸，但意味着**静态扫描脚本文本不能当安全边界**，安全只能靠「宿主函数只有白名单这几个」。`while(true){}` 在 200 毫秒 deadline 后 203 毫秒被打断，8MB 内存上限下的大分配在 2 毫秒内报错，两者都只给出**同一个通用异常**（`Exception generated by QuickJS`），无法从错误对象本身区分——所以中断处理器必须自己置一个 flag，由外层把它翻译成 `timeout` 与 `memory` 两个可区分的错误码，否则调用方拿到的永远是「脚本抛了个异常」。至于驱动：宿主函数不驱动时 `Promise::finish()` 直接返回「blocking on a promise resulted in a dead lock」，**且宿主函数的函数体根本没执行**（调用计数为 0）；驱动之后同一次调用 51 毫秒正常 settle。这条既坐实了 `drive()` 的必要性，也给测试提供了一个确定的失败签名。最后，外层 deadline 确实能兜住宿主在途：宿主睡 10 秒的调用被 300 毫秒的 `timeout` 在 302 毫秒处收住，脚本的 `await` 就此作废，进程继续可用。
