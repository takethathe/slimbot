# 工具审批以「回合结束 + 下一轮兑现」表达，不阻塞等待用户

个人 agent 的工具调用需要可控风险：工具声明**风险级**（只读 / 工作区写入 / 命令执行 / 网络外出 / 对外发送，不可配置），配置把风险级映射到三档**管控**——普通（直接执行）、中级（需 owner 确认）、高级（直接拒绝）。中级管控的做法是：中止该次调用、把动作（工具 + 参数全文 + 参数哈希）记为一条 **Pending approval**、以提问结束本轮；owner 在**下一轮**表态后，模型重新发起同一个调用，agent 比对参数哈希放行——即 **Approval redemption**。我们刻意**不做**阻塞式等待，也刻意**不提供任何 `ask_user` / `confirm` 类工具**（subagent 同样不提供；MCP 的 `elicitation` / `sampling` 不启用）：阻塞等待需要一个"可回放的挂起 Run"状态机，而 `RunState` 不持久化，用回合本身承载等待既复用现有循环，也不会让一个 Run 悬挂数小时。

**Considered Options**

- 阻塞式 hook 等待 UI 回调：需要挂起 Run 的持久化与恢复，且与"无认证、仅本机 WebUI"（ADR 0010）叠加后会造出一个必须在线才能推进的 agent。
- `ask_user` 工具：把"停下来问"建模成一次工具调用，本质上仍是阻塞，且让模型可以随时暂停整条链路。
- 文本匹配否决（否定词表）：**已证伪**。待确认的动作本身可能就含否定词（提议"取消订阅"，owner 回"确认取消"会被误判为拒绝），任何词表都无法区分"否定词是意图"还是"否定词是被批准动作的一部分"。

**Consequences**

- 这套机制的真保证是**不允许借一次批准去跑另一个操作**（参数哈希绑定 + 执行前重校验 + TTL 上界）；它**不保证 owner 确实同意了**——owner 那句话只有模型能读，一个困惑的模型在"算了"之后重放同一调用仍会放行。这是显式接受的残余风险，兜底靠**执行前广播** `ApprovalRedeemed` 事件（owner 可立即 `/stop`）与 trace 审计，不靠预防。
- 无人值守来源（cron / heartbeat / trigger / subagent）产生的中级管控一律按拒绝处理、不写入清单，因为没有"下一轮"能兑现它。
- 确认引导由 **agent 注入的一条 tool result** 承载（与第一轮那个 `tool_call` 天然配对），而**不是** `runtime_content` 每轮重注入：前者是模型已经习惯的结果通道，后者会造成同一个行为两个驱动源。它在确认轮内必须留在上下文（因此需要从 compact / snip 中豁免），确认轮结束时按兑现与否分别处理：**已兑现**——把真实工具结果改挂回第一轮那个 `tool_call`，删掉确认轮的重复调用与"确认"这句用户消息（模型看到的是一轮完整跑完）；**未兑现（未确认或否决）**——引导 tool result **不能直接消失**（会留下没有结果的 `tool_call`，模型会把它当作被截断的调用而重试），必须**改写为执行失败文案**。因此不变量是：**每个 `tool_call` 在历史里永远有一个真结果**，要么真实输出、要么失败文案，不存在悬空。模型的"请确认"消息与确认句仍需删除（它们不对应任何待配对调用，留着才会误导模型反复要求确认）；所有确认相关消息都带 `approval_id` 标记，由 PreChat 的纯函数 `merge_approval_rounds` 在**构建上下文时**清除（不重写 JSONL，保持 append-only）——不允许存在无标记的确认引导文本，否则它会随 session 永久残留。
